## 一、結論摘要

1. **問題**：網站一開啟就下載全部文明、全部時期的資料。壓縮後總量 1,217 KB，已達上限 1,500 KB 的 81.1%，只剩約 283 KB。再加一個日本規模的文明（各資料夾單獨壓縮估算約 261 KB）會讓總量來到約 1,478 KB，幾乎用完餘裕；之後只要再補一些資料，就很可能超標。新增歐洲、中亞等文明時，超標的風險很高。最大單檔是否超過 1,000 KB，則要看新資料打包進哪一個檔案。
2. **建議**：改成「總目錄＋資料包」架構。一開始只下載程式與精簡的總目錄，切到哪個文明、哪個時期才下載那一包。所有跨資料集的關聯（包括人物彈窗、戰役彈窗目前在瀏覽器端動態推導的部分）改在建置時算好。
3. **附帶整理**：文明改成註冊制，以明確的「文明能力介面」取代散落在程式各處的文明判斷。
4. **不變的部分**：網址格式、各頁顯示內容與數量、資料正本（`src/data/**/*.js`）、部署方式（GitHub Pages，不需後端）。預期的畫面變更只有兩項：推導關聯加上「程式推導」標示（需 Ivan 同意），以及切換到沒看過的資料包時短暫顯示載入中。
5. **做法**：分 6 個階段，依序推進。後面的階段依賴前面的成果，所以退回時要由後往前依序退回；關鍵的資料來源切換階段保留開關，可以切回舊做法。建議在待辦 2 之前完成。

## 三、目標架構

```text
建置時（npm run build）
  src/data/**/*.js（正本，不變）
        │ 正規化、建關係網、套用校正與政策、推導所有跨資料集關聯、換算地圖座標
        ▼
  dist/data/catalog.json                     總目錄（一開始就載入）
  dist/data/search-index.<雜湊>.json          搜尋索引（第一次使用搜尋時才載入）
  dist/data/packs/<資料包>.<雜湊>.json         資料包（切換時才載入）

瀏覽器
  入口程式 ──▶ catalog.json ──▶ 目前所需的資料包
                    │            └─ 切換時再抓下一包
                    └─ 使用搜尋時 ──▶ search-index
  地圖元件與底圖邊界資料：切到該文明時才載入
```

### 3.1 資料包的切分（維持現有畫面）

| 文明 | 一包的範圍 | 理由 |
|---|---|---|
| 華夏 | 一個時期（period）一包，共 10 包 | 與目前顯示單位一致 |
| 臺灣 | 整個文明一包 | 目前年表、人物誌、戰役錄、標頭數量都是整個文明的資料 |
| 日本 | 整個文明一包 | 同上 |

- 臺灣、日本若要再按時期拆包，會改變年表、人物誌與標頭數量的顯示方式，屬於產品變更，不在這次範圍內。日後日本資料包過大時再另案評估，屆時需要另外設計跨時期的人物與戰役索引。
- 新增文明時，依該文明的資料量與顯示方式選擇切分單位，寫在文明設定中（見 3.7）。

### 3.2 資料包內容

| 欄位 | 內容 |
|---|---|
| `meta` | `schemaVersion`、資料包 ID、文明（不放全域 `buildId`，也不放內容雜湊；雜湊只存在檔名與總目錄中，見 3.6） |
| `events`、`figures`、`battles` | 已正規化、已套用校正與政策的紀錄 |
| `territories`、`demographics` | 華夏各時期專用（臺灣、日本沒有則省略） |
| `warlordPeriods` | 地圖勢力快照：華夏各時期（`warlordPeriods`）與日本（`JAPAN_WARLORD_PERIOD_CONFIGS`）；臺灣若無則省略。屬歷史內容，見 3.7 |
| `eras` | 臺灣、日本的時期資訊，只放 `id`、`name`、`dateRangeDisplay`、`tagline`、`highlightFigures`、第一筆事件 key 等描述欄位，**不含 `keyEvents`**，避免事件重複存放；地圖與選單從本包的 `events`（`eraId`）、`battles`（`eraId`）取得內容。取代目前 `Header.jsx`、`TaiwanAtlasMap.jsx` 直接引入原始資料 |
| `links` | 建置時推導好的跨資料集關聯（見下） |

建置時推導、存進 `links` 的關聯，涵蓋 2.5 表中所有瀏覽器端動態推導的項目：

- 人物：參與事件、人物關係（含反向關係，最多 8 位，規則與現行 `figureRelations` 相同）、參戰紀錄（規則與現行 `FigureModal.js` 相同）
- 戰役：相關人物、相關事件
- 事件：相關人物、戰役

每個關聯目標以「描述」表示：`{ key, homePack, type, id, name, 顯示所需的最少欄位, derived, basis, review }`。

- `derived`：是否為程式推導（非資料中明確寫出的關聯）。
- `basis`：推導依據，例如明確 ID、指揮官名稱比對、戰役摘要文字比對、反向關係。現行參戰紀錄會以人物姓名比對指揮官甚至戰役摘要，可能只是文字命中，所以必須保留依據，畫面上不能讓推導結果看起來像已確認的史實關係。
- `review`：沿用現有的待確認、背景人物等審查狀態。
- 推導結果只存在資料包中，不回寫資料正本。
- **畫面標示**：現行人物彈窗的「參戰會戰紀錄」直接列出文字比對命中的戰役，沒有說明是推導的。為落實資料誠信，2a 起對 `derived` 為真的關聯加上「程式推導」標示，滑鼠移過或點擊時顯示依據。這是小幅畫面變更，需 Ivan 同意（見第七節），並納入階段 0 基準的預期差異。

彈窗可以直接畫出名牌，不必先下載目標資料包；使用者點下去時才載入目標資料包並開啟。

推導規則寫成**純函式**（輸入資料、輸出關聯，不依賴瀏覽器或檔案），放在建置與瀏覽器都能引用、但本身不引入資料正本的模組中。階段 1 的建置器、階段 2a 的過渡做法都呼叫同一套函式，確保結果一致。

### 3.3 實體身份與重複人物

- 每筆實體的唯一識別：`key = <資料集ID>:<類型>:<ID>`，例如 `republicModern:figure:jiang_zhongzheng`。
- 每筆實體只有一個「正式所屬資料包」（`homePack`）。
- 實體每出現在一個資料包，就是一次「出現」（`appearancePack`）。臺灣資料包需要顯示的華夏人物，以「參照副本」放入：內容在建置時從正式所屬資料包複製，並標記 `ref: <key>`，不另外維護，所以不會產生資料分歧。
- **使用哪一個資料包**：
  - 從臺灣人物誌、臺灣年表、臺灣頁的搜尋結果點選時，載入 `appearancePack`（臺灣），停留在臺灣頁開啟。
  - 點選關聯（彈窗中的人物、事件、戰役名牌）時：**目前資料包裡有這個實體的出現，就留在目前資料包開啟；沒有才前往 `homePack`**。這與現行 `handleSelectFigure` 先找目前人物清單的做法相同（`app.js` 約第 355 行），例如在臺灣頁從鄭芝龍點到顏思齊，現在不會跳回元明時期，之後也不會。
- **搜尋維持現有行為**：
  - 同一實體出現在幾個資料包，就列幾筆結果，搜尋結果的識別為 `<key>@<appearancePack>`，結果與排序和現在相同。
  - 若日後要改成每人只列一筆，屬於搜尋產品行為變更，另案交 Ivan 決定。

### 3.4 總目錄與搜尋索引

**總目錄（catalog.json，一開始就載入）**

| 內容 | 用途 |
|---|---|
| `schemaVersion`、`buildId` | 版本比對 |
| 文明清單、各時期名稱、年份範圍、事件／人物／戰役數量 | 選單、標頭數字 |
| 各資料包的檔名（含雜湊）與大小 | 下載與快取 |
| 同期對照索引：事件 key、年份、標題、文明、時期、建置時算好的政權名稱 | 同期東亞對照 |
| 搜尋索引檔名 | 延後載入搜尋索引 |

**搜尋索引（search-index，第一次聚焦搜尋框時才載入）**

- 包含現行搜尋比對的全部欄位，以及組成副標題所需的欄位，確保搜尋結果與排序和現在相同。
- 每筆是一次「出現」，附上 `key`、`appearancePack`、`homePack`（見 3.3）。點搜尋結果時：先載入 `appearancePack`，再開啟該實體；載入失敗或已被新的操作取代時，不開啟舊結果。
- 載入狀態：
  - 第一次聚焦搜尋框時開始載入，顯示「搜尋索引載入中」
  - 載入期間輸入的文字保留，載入完成後立即執行搜尋，不能短暫顯示「沒有結果」
  - 載入失敗時顯示錯誤訊息與重試按鈕
- 搜尋索引會隨資料成長，單獨設大小上限；必要時再按文明拆開。

### 3.5 載入流程與網址導覽

- **兩段式導覽**：
  1. 解析網址，用總目錄找出需要的資料包
  2. 載入資料包
  3. 依網址選取事件、人物、戰役
  
  資料包載入完成之前，不得用預設值覆寫網址中的深層連結參數。
- **競態處理**：每次載入帶一個請求序號，或使用 `AbortController`。快速連續切換、上一頁／下一頁、重複請求時，只採用最新一次請求的結果，晚到的舊回應直接丟棄。
- **總目錄是所有流程的前提**：
  - 首次開啟時顯示載入中
  - 網路錯誤、404、JSON 損毀時，顯示錯誤訊息與重試按鈕
  - `schemaVersion` 不支援時，顯示「網站已更新，請重新整理」
  - 重試時強制重新向伺服器驗證、不使用本地快取，次數有上限（數字在 2b 訂定）
- **載入中狀態**：切到沒看過的資料包時顯示載入中；失敗時顯示錯誤訊息與重試按鈕，不能只留空白。
- **快取**：
  - 資料包與搜尋索引的檔名含內容雜湊，可長期由瀏覽器快取（HTTP 快取）。GitHub Pages 的快取標頭不由我們控制，以實測為準。
  - 本機預覽伺服器 `server.cjs` 目前只對 `app.<雜湊>`、`chunk.<雜湊>` 的 JS、CSS 回應長期快取，所有 `.json` 都是 `no-cache`。階段 1 要擴充為 `packs/*.<雜湊>.json` 與 `search-index.<雜湊>.json` 長期快取、`catalog.json` 維持 `no-cache`，並新增自動測試檢查 HEAD 請求、Content-Type、Cache-Control。
  - 已解析的資料包在記憶體中最多保留 N 包，超過時移除最久沒用的（N 待階段 2b 實測記憶體用量後訂定）
  - 記憶體快取以「含雜湊的檔名」為鍵，不以資料包 ID 為鍵；取得新總目錄後，雜湊相同的資料包保留，雜湊改變的移除；搜尋索引檔名改變時同樣失效

### 3.6 版本一致性

- 資料包與搜尋索引都以內容雜湊命名，由總目錄指向，避免部署後「新目錄配舊資料包」。
- 全域 `buildId` 只放在總目錄。資料包的內容雜湊由建置時對資料包內容計算，只寫在檔名與總目錄中，不寫進資料包本身（避免循環定義）。某個時期的資料沒變，它的檔名就不變，瀏覽器快取繼續有效；只有實際改動的資料包才需要重新下載。
- 總目錄不使用長期快取。取得新總目錄後依 3.5 的規則更新記憶體快取；`schemaVersion` 不相容的資料包一律移除。
- 遇到 404 或 `schemaVersion` 不符時，重新抓一次總目錄。仍失敗就顯示「網站已更新，請重新整理」，不無限重試。

### 3.7 文明註冊制與能力介面

```text
src/civilizations/
  registry.js           文明清單
  china/config.js
  taiwan/config.js
  japan/config.js
```

每個文明的設定必須提供以下能力，主程式只透過這個介面使用，不再寫「如果是日本就……」：

| 能力 | 說明 |
|---|---|
| 基本資料 | ID、名稱、預設時期 |
| 網址參數 | 使用 `period` 或 `civ`＋`era`，以及預設值 |
| 資料包切分單位 | 依時期或依整個文明（見 3.1） |
| 地圖載入 | 延後載入的地圖元件、需要的底圖資料 |
| 陣營 | 陣營名稱與樣式（取代 `factionConfig.js` 的分支） |
| 同期對照 | 顯示名稱、排序、政權名稱判斷（建置時使用） |
| 選用功能 | 例如人口統計，有提供才顯示 |
| 實體歸屬 | 哪些人物屬於本文明、哪些是其他文明的參照 |

- 新增文明的工作是：新增一個資料夾與設定檔、準備資料正本與地圖、在註冊清單加入一筆。地圖元件與資料仍需各自製作，不是「加一行就完成」。
- **硬性邊界**：

  | 類別 | 例子 | 可以出現在哪裡 |
  |---|---|---|
  | 歷史內容資料（事件、人物、戰役、勢力範圍、人口、地圖勢力快照、時期內容、來源對照、連結校正表） | 例如 `periods/**` 的事件、人物、戰役、勢力範圍、人口、勢力快照檔，`threeKingdoms/` 的同類檔案（`chinaMapData.js` 除外），`taiwanLensData.js`，`japan/japanEras.js`、`japanFigures.js`、`japanBattles.js`、`japanWarlordPeriods.js`，`sourceReferences.js`，`linkedHistoryCatalog.js` | 只能由建置專用轉接程式引入（`build.cjs` 或 `scripts/` 之下），經資料包送到瀏覽器；瀏覽器端唯一例外是 2b 的回退分包，階段 4 移除 |
  | 地圖用的地理資料（邊界、投影、底圖標註） | 例如 `threeKingdoms/chinaMapData.js`、`japan/japanPrefecturesGeoData.js`、`japan/japanMapGeoData.js`、臺灣邊界資料 | 只能在延後載入的地圖分包中 |
  | 小型設定與純函式 | `factionConfig.js`、`chronologyReviews.js` 這類規則或設定、3.2 的關聯推導函式 | 可以在主入口，但不得再引入歷史內容資料 |

  - **地圖勢力快照屬於歷史內容**（華夏的 `warlordPeriods`、日本的 `JAPAN_WARLORD_PERIOD_CONFIGS`），放進各自的資料包，由主程式以參數傳給地圖元件；地圖分包只保留邊界、投影與底圖標註。
  - **每個 `src/data/**/*.js` 檔案都必須恰好歸入一類**，分類清單在階段 1 建立並由測試讀取；有檔案未分類或重複分類時測試失敗。同一資料夾內可能混有不同類別（例如 `threeKingdoms/` 同時有歷史內容與 `chinaMapData.js`），所以按檔案逐一分類，不用整個資料夾歸類。目前有些設定檔是否混有內容資料（例如 `chronologyReviews.js`），在階段 1 逐一確認。
  - 以 esbuild 的 metafile 加一項自動測試：只追蹤**主入口的靜態依賴**，其中不得出現第一類的檔案。延後載入的分包另外檢查，只允許地圖分包含第二類、只允許 2b 指定的回退分包含第一類。
  - 現行 `JapanAtlasMap.jsx` 從 `japan/index.js` 引入，會連帶拉進日本的事件、人物、戰役；2b 要改成只引入允許的地理資料模組，勢力快照改由資料包傳入。`TaiwanAtlasMap.jsx` 引入整個 `taiwanLensData.js` 的問題同樣在 2b 處理。

### 3.8 地圖

- 日本、臺灣事件的地圖座標在建置時換算，資料包不再需要地圖邊界資料。
- 邊界資料只隨地圖元件延後載入。
- 共用世界底圖（多個地區共用一套地理資料、各自設定範圍與投影）留到實際新增歐洲或中亞時再評估，這次不做。

### 3.9 體積檢查標準（需 Ivan 同意）

| 代號 | 項目 | 計算方式 |
|---|---|---|
| A | 首次載入 | 在沒有快取的瀏覽器中，從開啟網址到該頁主要內容可以使用為止，實際請求的所有 JS、CSS、總目錄與資料包（含該頁立即觸發的延後分包，例如預設首頁的華夏地圖分包及其地理資料、人物誌或戰役錄深層連結的分包），以壓縮後的傳輸量計算。以瀏覽器的網路請求量測，不只從依賴關係推算。分別量「預設首頁」與「最壞情況的深層連結」，取較大者 |
| B | 最大單一資料包 | 壓縮後大小；另記錄解壓後大小與在手機上解析所需時間，作為參考 |
| C | 總目錄 | 壓縮後大小 |
| D | 搜尋索引 | 壓縮後大小 |
| E | 程式與結構化資料總量 | JS、CSS、總目錄、搜尋索引、全部資料包合計（含 2b 過渡期的舊做法程式），作為護欄，避免大量各自合格的小包無限成長。圖片不納入，圖片目前另有引用檢查，不另設體積上限 |

- B、C、D、E 的上限數字在階段 1 實測後提出；A 在階段 1 只能提出預估值，因為此時前端仍內嵌全部資料，量到的數字會把舊資料和新資料包重複計算。A 的正式量測與上限，要等 2b 移除所有靜態資料引入後再確認。現在都不預設數字。
- 這不是放寬標準，而是改成量使用者實際要等的下載量，同時保留總量護欄。
- 依 `AGENTS.md`，修改檢查標準要 Ivan 同意，並同步更新 `AGENTS.md` 與 `README.md`。

## 四、分階段實施

每個階段都要通過以下檢查，並在瀏覽器實測後才 commit、push：

- `npm run build`、`npm test`、`npm run verify`：必須通過
- `node scripts/validate_history_data.mjs --effective`：必須通過（套用校正與待確認隔離後的有效資料檢查）。目前 GitHub Actions 只執行 build、test、verify，**沒有**執行這一項；階段 1 將它加入 Actions 的發布流程，之後未通過就不會發布

## 六、風險與驗證

| 風險 | 對策 |
|---|---|
| 跨資料集關聯（含反向人物關係、參戰紀錄、戰役彈窗）改變或遺失 | 建置與 2a 共用同一套推導純函式；階段 0 基準逐筆比對 |
| 推導的關聯被誤當成已確認史實 | 關聯描述保留 `derived`、`basis`、`review`；2a 起畫面顯示「程式推導」標示與依據（需 Ivan 同意），既有的待確認標示照舊 |
| 搜尋結果或排序改變 | 搜尋索引保留現行全部比對欄位，並依「出現」列結果；以固定搜尋詞比對前 24 筆與排序 |
| 資料正本被註冊表或其他模組再次打包進入口 | 3.7 的硬性邊界與 metafile 自動測試 |
| 深層連結被預設值覆寫、快速切換時顯示錯誤內容 | 兩段式導覽、請求序號或 `AbortController` |
| 部署更新時目錄與資料包版本不一致 | 雜湊檔名、`schemaVersion` 與 `buildId` 比對、只重抓一次總目錄 |
| 手機網路慢或不穩 | 載入中狀態、錯誤訊息與重試；以慢速網路模擬實測 |
| 記憶體占用隨瀏覽時間增加 | 記憶體中的資料包數量設上限 |
| 總目錄、搜尋索引隨資料成長 | 3.9 的 C、D 單獨設限；必要時按文明拆開 |
| 2b 改動範圍大 | 2a 先把存取集中到一個模組；2b 保留開關 |

瀏覽器實測清單（2a 起每個階段）：

- 電腦與手機寬度
- 華夏、臺灣、日本各切換數個時期
- 直接開啟帶 `event`、`figure`、`battle`、`tab` 參數的網址（冷啟動）
- 全站搜尋並點選其他文明的結果
- 同期對照跳轉
- 人物誌、戰役錄；人物與戰役彈窗的關聯跳轉
- 劇院滿版地圖

2b 另外加測：

- 慢速網路
- 總目錄網路錯誤、404、損毀、不支援的 `schemaVersion`
- 資料包 404
- 損毀的 JSON
- 搜尋索引 404、損毀
- 搜尋索引載入中就輸入文字，接著切換文明
- 快速連續切換
- 載入中按上一頁
- 部署新版本時切換頁面
- 重試按鈕
