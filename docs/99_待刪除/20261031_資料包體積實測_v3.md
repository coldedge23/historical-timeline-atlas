## 一、結論摘要

1. 移除回退分包後，程式與資料總量（E）從 3,417 KB 降到 **2,446 KB**。E 上限重訂為 **3,200 KB**（2026-10-31 Ivan 核准），目前使用 76.4%。
2. 首次載入（A）最壞情況為三國地圖頁 **616.0 KB**（v2 為 617.7 KB，主程式少了回退開關），使用 77.0%。
3. A 改由 `npm run verify` 自動檢查：12 個頁面 × 3 個分頁（地圖、人物誌、戰役錄）共 36 種情境，取最大值。
4. 自動檢查算出的檔案清單，與瀏覽器實際請求逐一比對，9 個情境在電腦與手機寬度下都完全相同。

## 二、首次載入（A）

### 2.1 自動檢查的算法（`scripts/check_first_load.cjs`）

- 建置時把每個 JS 分包的靜態引入與對應的原始模組寫進 `dist/build-manifest.json` 的 `chunks`。
- 每種情境的檔案＝主程式及其靜態引入的分包＋CSS＋總目錄＋該頁資料包＋該分頁的延後分包（及其靜態引入）。
  - 地圖分頁：該文明 `config.js` 的 `loadMap` 所載入的地圖元件。
  - 人物誌、戰役錄：`app.js` 以 `lazy()` 載入的元件。測試會檢查兩邊清單一致（`tests/bundle-boundary.test.js`）。
- 以 `zlib.gzipSync` 計算壓縮後大小，與 B–E 用同一把尺。圖片與 `index.html` 不計入（3.9 的定義）。
- 搜尋索引在第一次點搜尋框時才下載，不計入 A。

### 2.2 與瀏覽器實測比對（2026-10-31）

- 量法同 v2：在瀏覽器以 iframe 開啟各情境網址（電腦寬 1,280 px、手機寬 375 px 各一次），等網路請求停止後記錄實際請求的 JS、CSS、總目錄與資料包。
- 結果：9 個情境 × 2 種寬度，瀏覽器請求的檔案清單與自動檢查算出的清單完全相同。
- 這是本機預覽伺服器的結果。GitHub Pages 實際傳輸量比 `gzipSync` 估算多約 4–5%（2b 實測）；上限仍以 `gzipSync` 計算，不另加係數（2026-10-31 Ivan 同意）。最壞情況加 5% 約 647 KB，仍在 800 KB 內。
- 何時要再用瀏覽器實測：新增文明、新增延後載入的分頁、改變分包方式，或首次載入使用率超過 90% 時。
